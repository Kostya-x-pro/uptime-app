# Гайд по миграциям базы данных

Этот документ описывает единый порядок создания, запуска, проверки и отката миграций в Uptime App. Он предназначен для разработчиков и агентов, которые изменяют схему PostgreSQL.

## Где находятся миграции

Миграции хранятся в каталоге `backend/migrations/` и состоят из двух файлов на каждую версию:

```text
backend/migrations/
├── 000001_create_auth_tables.up.sql
├── 000001_create_auth_tables.down.sql
├── 000002_add_user_avatar.up.sql
├── 000002_add_user_avatar.down.sql
├── 000003_create_monitors.up.sql
└── 000003_create_monitors.down.sql
```

Файлы с суффиксом `.up.sql` применяют изменение, а файлы с `.down.sql` отменяют его. Версия определяется числовым префиксом; он должен быть уникальным и больше текущей последней версии.

Запуск выполняется в `backend/internal/platform/migrations.go` библиотекой `github.com/golang-migrate/migrate/v4`. Перед созданием соединения с БД приложение вызывает `migrate.Up()`, поэтому при старте API применяются все ещё не применённые миграции. Путь к каталогу задаётся переменной `MIGRATIONS_DIR` и по умолчанию равен `migrations`.

Приложение не запускает отдельную команду миграции и не использует ORM-автомиграцию. Миграции выполняются как часть старта API; при деплое нескольких экземпляров применяйте один и тот же набор файлов и контролируйте логи старта каждого экземпляра.

## Перед началом работы

1. Создайте отдельную ветку от актуального `main` согласно [правилам веток и PR](../rules/branches-and-pr.md).
2. Проверьте, что рабочее дерево чистое, и убедитесь, что нужная база данных доступна.
3. Определите, как изменение будет развертываться на уже заполненной базе. Миграция должна сохранять существующие данные или явно описывать безопасный план их преобразования.
4. Не добавляйте в миграции секреты, локальные пути, `.env` и данные, зависящие от конкретного окружения.

## Создание миграции

### 1. Выберите следующую версию

Посмотрите последнюю версию в `backend/migrations/` и увеличьте её на единицу. Например, следующая миграция после `000003` будет называться `000004_add_monitor_labels`.

Не переиспользуйте номер уже применённой миграции и не редактируйте старые `.up.sql` или `.down.sql` после попадания изменений в общую ветку. Для исправления схемы создаётся новая миграция.

### 2. Создайте пару файлов

```text
backend/migrations/000004_add_monitor_labels.up.sql
backend/migrations/000004_add_monitor_labels.down.sql
```

В `.up.sql` добавьте только изменение, необходимое для текущей задачи. В `.down.sql` опишите обратную операцию в том же порядке зависимостей. Например:

```sql
-- 000004_add_monitor_labels.up.sql
ALTER TABLE monitors ADD COLUMN label VARCHAR(100) NOT NULL DEFAULT '';
```

```sql
-- 000004_add_monitor_labels.down.sql
ALTER TABLE monitors DROP COLUMN label;
```

Для обязательных полей на таблицах с данными используйте поэтапное изменение: сначала добавьте nullable-колонку или безопасное значение по умолчанию, заполните существующие строки, затем отдельной миграцией добавьте ограничение. Для больших таблиц оцените блокировки и время выполнения до запуска в production.

### 3. Синхронизируйте код приложения

Если меняются поля или ограничения, обновите соответствующие Go-модели, репозитории, обработчики и документацию API. Не рассчитывайте на ORM-автомиграцию: схема изменяется только SQL-файлами в `backend/migrations`.

Проверьте, что миграция обратима без потери нужных данных. Если откат по смыслу разрушителен (например, удаляет колонку), явно укажите это в описании PR и не используйте такой `down` для production без резервной копии и согласованного плана.

## Локальный запуск

### Запустить только PostgreSQL

Из корня репозитория:

```powershell
$env:JWT_SECRET = "at-least-32-random-characters-long"
docker compose up -d postgres
```

Для локального запуска Go-сервиса переменные подключения должны указывать на опубликованный Compose-порт:

```powershell
$env:DATABASE_URL = "postgres://uptime:uptime@localhost:5433/uptime?sslmode=disable"
$env:JWT_SECRET = "at-least-32-random-characters-long"
$env:MIGRATIONS_DIR = "migrations"
go run ./cmd/server
```

Команды Go выполняются из `backend/`. При старте сервиса миграции из `MIGRATIONS_DIR` применяются автоматически. Если миграций нет, запуск продолжается с сообщением `no change` на уровне библиотеки.

### Запустить API через Docker Compose

Из корня репозитория:

```powershell
$env:JWT_SECRET = "at-least-32-random-characters-long"
docker compose up --build
```

В контейнере каталог `backend/migrations` копируется в `/app/migrations`, поэтому значение `MIGRATIONS_DIR` по умолчанию подходит. Сервис API не должен считаться готовым, пока его старт не завершился после успешного применения миграций.

## Проверка результата

Проверяйте миграцию в следующем порядке.

### 1. Проверка файлов и формата

Из корня репозитория:

```powershell
Get-ChildItem backend/migrations -File | Sort-Object Name
```

У каждой версии должна быть ровно одна пара `.up.sql` и `.down.sql`, номера не должны повторяться, а SQL должен соответствовать PostgreSQL 17, используемому в Compose.

### 2. Проверка состояния миграций

Таблица `schema_migrations` создаётся `golang-migrate` и содержит текущую применённую версию и флаг `dirty`. Проверить её можно через `psql` внутри контейнера:

```powershell
docker compose exec postgres psql -U uptime -d uptime -c "SELECT version, dirty FROM schema_migrations;"
```

Ожидаемый результат после успешного запуска:

- `version` совпадает с номером последней миграции;
- `dirty` равен `f` (`false`);
- повторный запуск API не изменяет схему и завершается без ошибки.

Если таблица `schema_migrations` отсутствует, приложение подключено не к той базе или не дошло до запуска мигратора.

### 3. Проверка самой схемы

Проверьте новые таблицы, колонки, индексы и ограничения:

```powershell
docker compose exec postgres psql -U uptime -d uptime -c "\d+ monitors"
docker compose exec postgres psql -U uptime -d uptime -c "SELECT table_name, column_name, data_type FROM information_schema.columns WHERE table_schema = 'public' ORDER BY table_name, ordinal_position;"
```

Затем запустите проверки изменённого модуля:

```powershell
Set-Location backend
go test ./...
go vet ./...
```

Если изменение затрагивает frontend или API-контракт, дополнительно выполните из `frontend/`:

```powershell
npm.cmd run lint
npm.cmd run build
```

### 4. Проверка прикладного поведения

После успешной миграции проверьте затронутый сценарий через API или интерфейс: чтение старых записей, создание и обновление новых записей, значения по умолчанию и работу ограничений. Отдельно убедитесь, что существующие пользователи и мониторы сохранились.

## Ошибка и восстановление

Если запуск остановился с ошибкой миграции:

1. Остановите API, чтобы новые запросы не выполнялись на частично изменённой схеме.
2. Сохраните полный текст ошибки и проверьте состояние:

   ```powershell
   docker compose exec postgres psql -U uptime -d uptime -c "SELECT version, dirty FROM schema_migrations;"
   ```

3. Если `dirty = t`, не запускайте приложение повторно вслепую и не изменяйте строку в `schema_migrations` вручную. Разберите причину, сделайте резервную копию и выберите восстановление или исправляющую миграцию.
4. Для локальной базы без важных данных допустимо пересоздать Compose-том:

   ```powershell
   docker compose down -v
   docker compose up -d postgres
   ```

   Команда удаляет локальные данные и не применяется к базам с нужной информацией.
5. Для production используйте резервную копию и согласованный план восстановления. Не выполняйте `down` на production как обычный способ исправления ошибки.

После восстановления повторите запуск с исправленной последовательностью миграций и пройдите все проверки из раздела «Проверка результата».

## Краткий чек-лист агента

Перед завершением задачи агент должен убедиться, что:

1. Новая миграция имеет следующий уникальный номер и пару `.up.sql`/`.down.sql`.
2. Старые миграции не изменены, а SQL не содержит секретов и окружение-зависимых значений.
3. Код приложения и API используют новую схему, если изменялись таблицы или поля.
4. Локальный API стартует с миграцией на чистой базе и повторно стартует без ошибки.
5. В `schema_migrations` указана последняя версия, а `dirty = false`.
6. Проверены существующие данные, новые ограничения и прикладной сценарий.
7. В PR описаны схема, обратимость, риск потери данных и команды проверки.

## Требования к PR

В PR с миграцией укажите:

- номер и назначение новой миграции;
- какие таблицы, колонки, индексы и ограничения изменены;
- как сохраняются и преобразуются существующие данные;
- является ли откат безопасным и какие данные он удаляет;
- команды проверки и их результаты;
- изменения API-контракта, если они есть.

Не включайте в PR `.env`, дампы баз данных, секреты и файлы из `node_modules/` или сборки.
